# 粮知 App V0.1.0 实施计划

> 文档用途：供 AI 开发者逐步执行
> 目标平台：iOS、Android
> 应用标识：`com.liangzhi.app`
> 推荐技术栈：Flutter、Dart、Riverpod、Drift/SQLite、go_router、条形码扫描、Open Food Facts、本地通知
> 当前范围：基础应用、手动录入、条形码扫码录入和四类本地通知
> 原则：每一步都必须独立完成、独立验证，验证失败时不得进入下一步

---

## 1. 实施目标

本阶段的目标是交付一个稳定、可运行、可继续扩展的基础应用。完成后，应用应具备：

- 可在 Android 和 iOS 模拟器或真机上启动；
- 统一的工程结构和命名规范；
- 基础主题、字体、间距和颜色体系；
- 底部导航和主要页面框架；
- 本地 SQLite 数据库；
- 基础食品数据模型；
- Repository 数据访问层；
- Riverpod 状态管理基础；
- 首页、到期提醒、扫码添加、全部食物、我的五项导航；
- 基础食品列表、手动添加和详情页；
- 一维商品条形码扫描；
- Open Food Facts 只读查询、本地缓存和手动补充回退；
- 临期、今日到期、已过期汇总和长期未更新四类本地通知；
- 本地设置存储；
- 空状态、加载状态和错误状态；
- 单元测试、组件测试和基础集成测试；
- 清晰的构建、检查和验收流程。

本阶段不实现：

- 用户注册和登录；
- 云同步；
- 家庭共享；
- AI 识别；
- 在线食谱；
- 完整统计；
- 复杂搜索和筛选；
- 正式埋点和商业化能力。

---

## 2. 总体执行规则

### 2.1 小步提交

每完成一个步骤，应单独提交一次版本记录。提交信息应描述完成的具体事项，不应使用“更新代码”“修复问题”等模糊表述。

**验证测试：**

- 查看版本记录，确认每个步骤对应独立提交；
- 随机选择一个提交，确认其只包含该步骤相关改动；
- 确认不存在一次提交同时修改大量无关模块的情况。

### 2.2 先验证后继续

每一步完成后，必须执行该步骤指定的测试。测试未通过时，先修复当前步骤，不得继续后续步骤。

**验证测试：**

- 在实施记录中保留每一步的测试结果；
- 确认所有已标记完成的步骤均有对应验证结果；
- 确认不存在“跳过测试”后继续开发的步骤。

### 2.3 不提前实现完整功能

本阶段只实现本文档与 `architecture.md` 明确的基础结构、扫码、通知和最小闭环。遇到尚未定义的业务细节时，使用占位内容、默认值或待办标记，不自行扩展需求。

**验证测试：**

- 检查依赖列表，确认除 Open Food Facts 和本地通知外，未加入云同步、AI、推送或其他在线商品库依赖；
- 检查页面，确认没有超出本计划范围的大型功能；
- 检查待办列表，确认未确定需求被记录而非自行实现。

# 阶段二：代码质量与工程约束

## 步骤 6：启用统一静态检查规则

启用 Flutter 官方推荐的 lint 规则，并增加团队需要的基础规则，例如：

- 禁止未使用的导入；
- 禁止隐式动态类型；
- 鼓励使用不可变对象；
- 要求公开 API 有明确类型；
- 禁止调试输出进入正式代码。

**验证测试：**

- 执行静态检查；
- 确认结果为零错误；
- 人为加入一个未使用导入，确认检查能够发现；
- 删除测试错误后再次确认检查通过。

## 步骤 7：统一格式化规则

使用 Dart 官方格式化工具作为唯一格式标准，不引入第二套格式化方案。

**验证测试：**

- 对整个项目执行格式化；
- 再次执行格式检查；
- 确认没有文件需要继续格式化；
- 确认团队成员使用相同格式化命令可得到一致结果。

## 步骤 8：建立命名规范文档

在项目文档中记录：

- 文件名使用小写下划线；
- 类名使用大驼峰；
- 变量和方法使用小驼峰；
- Provider 名称使用统一后缀；
- 页面文件使用 `page` 后缀；
- 可复用组件使用 `widget` 或明确业务名称；
- 数据表、字段和模型名称保持一致。

**验证测试：**

- 随机检查至少十个文件和类；
- 确认命名与文档一致；
- 确认不存在同一概念使用多套命名的情况。

## 步骤 9：建立基础持续检查命令

在项目文档中定义每次提交前必须执行的命令，并建立 GitHub Actions：

- 获取依赖；
- 格式化；
- 静态检查；
- 单元测试；
- 组件测试。

CI 要求：

- Linux Runner 执行格式检查、`flutter analyze`、全部测试和 Android 构建；
- macOS Runner 执行 `flutter build ios --no-codesign`；
- CI 不依赖签名证书、个人本地路径或未声明的环境变量。

**验证测试：**

- 从干净环境执行完整检查流程；
- 确认所有命令均可成功运行；
- 确认流程不依赖个人本地的特殊配置。

# 阶段三：目录和架构骨架

## 步骤 10：建立应用级目录

建立以下应用级目录：

- `app`：应用入口、路由、主题；
- `core`：数据库、存储、公共服务、错误定义；
- `features`：按功能组织页面和状态；
- `shared`：跨功能复用组件和模型。

不要建立多余的五层或六层架构。

**验证测试：**

- 检查目录结构；
- 确认每个目录职责清晰；
- 确认不存在 `utils`、`helpers`、`common` 等职责不明的大杂烩目录。

## 步骤 11：建立功能模块目录

在 `features` 下建立基础模块：

- home；
- expirations；
- scan；
- foods；
- add_food；
- food_detail；
- mine。

每个模块只创建当前需要的子目录，例如页面、状态和组件，不预建大量空目录。

**验证测试：**

- 检查每个功能模块；
- 确认没有空目录或未使用模板文件；
- 确认同一功能的文件没有散落到多个位置。

## 步骤 12：建立依赖方向规则

明确依赖方向：

- 页面可以依赖状态和共享组件；
- 状态可以依赖 Repository；
- Repository 可以依赖本地数据库；
- 数据库不得依赖页面或状态；
- `core` 不得依赖具体功能页面；
- 功能模块之间不得直接访问彼此的内部实现。

**验证测试：**

- 检查现有导入关系；
- 确认不存在数据库导入页面文件；
- 确认不存在功能模块绕过 Repository 直接访问数据库；
- 确认不存在循环依赖。

**验证测试：**

- 人为触发一个页面构建错误；
- 确认开发环境可以看到明确错误信息；
- 确认正式展示不会暴露堆栈；
- 确认应用没有直接退出。

# 阶段五：设计系统基础

## 步骤 16：定义颜色体系

以 `memory_bank/ui/styles.css` 为视觉来源定义应用基础颜色角色，而不是在页面内直接写颜色值。基础值包括：

- 强调色 `#3F854C` 和深强调色 `#2F6E3C`；
- 主背景 `#FFFFFF` 和次级背景 `#F7F6F2`；
- 主文本 `#191B18` 和次级文本 `#777B75`；
- 分隔线 `#E8E9E5`；
- 柔和成功背景 `#EDF5EE`；
- 临期色 `#FFB547`；
- 错误/过期色 `#F02D23`。

颜色命名应表达用途，不应只表达色值。

**验证测试：**

- 搜索页面代码，确认没有散落的直接颜色值；
- 在浅色模式下检查所有基础颜色；
- 确认文字与背景对比清晰；
- 确认状态色不会大面积制造视觉压力。

## 步骤 17：定义字体层级

沿用 UI 原型的中文平台字体策略：iOS 优先 PingFang SC，Android 使用系统可用的中文无衬线字体。定义统一文本样式，至少包括：

- 页面大标题；
- 区块标题；
- 食品名称；
- 正文；
- 辅助说明；
- 状态标签；
- 按钮文字。

**验证测试：**

- 在占位页面展示全部文本层级；
- 确认层级差异清晰；
- 确认没有页面自行创建重复文本样式；
- 在小屏设备上确认无明显截断。

## 步骤 18：定义间距和圆角规范

建立统一间距等级和圆角等级。页面与组件只能使用预定义等级，不直接使用随意数值。

**验证测试：**

- 检查首页、列表和“我的”页面；
- 确认主要边距保持一致；
- 确认卡片和按钮圆角统一；
- 确认没有视觉上明显不一致的间距。

## 步骤 19：建立应用主题

将颜色、字体、按钮、输入框、卡片、底部导航和弹窗基础样式统一放入主题配置。

首版只要求浅色主题。暗色主题保留扩展能力，不在本阶段实现。

`memory_bank/ui/` 决定视觉风格，PRD、`architecture.md` 和本文档决定功能范围；不得把原型中的静态库存、关联食谱或不可用按钮直接实现为业务功能。

**验证测试：**

- 启动应用并逐页检查；
- 确认按钮、输入框和卡片样式一致；
- 临时替换主题主色，确认主要组件能够统一变化；
- 确认页面没有大量覆盖主题的局部样式。

## 步骤 20：建立基础图标策略

统一使用一套系统图标风格。首版不混用多套第三方图标。

**验证测试：**

- 检查底部导航和页面操作图标；
- 确认线条粗细和视觉风格一致；
- 确认不存在同一功能使用不同图标的情况。

# 阶段十七：条形码扫码与远程商品查询

## 步骤 78：建立远程商品查询接口

建立与 UI 和第三方 API 解耦的 ProductLookupRepository。输入为规范化条形码，输出为命中、未命中或统一错误，不暴露 HTTP 响应对象。

**验证测试：**

- 使用假实现返回命中、未命中、超时、限流和服务错误；
- 确认上层状态完整且不依赖 HTTP 类型；
- 确认生产环境只允许 HTTPS。

## 步骤 79：接入 Open Food Facts

使用固定版本只读商品接口，携带 `cc=cn`、`lc=zh`、`tags_lc=zh`、最小字段集合和规定 User-Agent。只读取名称、品牌、规格、图片和分类标签。

**验证测试：**

- 查询一个已知条形码并核对映射字段；
- 查询未收录条形码并返回未命中；
- 验证请求不包含库存、数量、生产日期、到期日期或备注；
- 验证 404、429、5xx、超时和无网络均转换为统一错误。

## 步骤 80：实现条码商品缓存

按 `architecture.md` 建立并使用 `barcode_product_cache`：先查本地缓存，再请求远程；命中缓存 30 天，未命中缓存 24 小时；不保存完整远程响应。

**验证测试：**

- 首次查询访问远程，第二次查询命中本地；
- 模拟缓存过期并确认刷新；
- 刷新失败时确认可展示旧值并要求确认；
- 清除数据后确认缓存为空。

## 步骤 81：实现相机条形码扫描

只启用一维商品条形码格式：EAN-8、EAN-13、UPC-A、UPC-E、Code 128。配置 Android/iOS 相机权限说明和权限拒绝状态，不解析二维码。

**验证测试：**

- 扫描每类支持的测试条形码；
- 二维码不得进入商品查询；
- 拒绝相机权限时显示说明和系统设置入口；
- 同一条码连续出现时只触发一次查询。

## 步骤 82：实现扫码结果与分类建议

远程命中后展示名称、品牌、规格和图片，并按 `architecture.md` 映射本地分类建议。建议值必须可编辑；远程图片失败不得阻断保存。

**验证测试：**

- 验证各分类关键词映射；
- 未匹配分类回退“其他”；
- 图片加载失败显示本地占位；
- 远程结果缺字段时页面仍可完成录入。

## 步骤 83：实现扫码保存闭环

扫码只负责商品基础信息；用户仍必须输入直接到期日期，或生产日期加保质期。保存后写入食品、条码、用户确认后的品牌/规格和可用图片路径，并返回全部食物页面。已保存食品不得被后续远程缓存刷新静默覆盖。

**验证测试：**

- 远程命中后补充到期信息并保存；
- 缺少到期信息时阻止保存；
- 同一条码允许保存多个不同批次；
- 保存后列表、详情和缓存内容正确。

## 步骤 84：实现未命中与离线回退

远程未命中、无网络、超时或服务不可用时，进入预填条形码的手动添加页，不显示阻断式失败页。

**验证测试：**

- 分别模拟未命中、离线、超时、429 和 5xx；
- 确认条形码保留且用户输入不丢失；
- 手动补充保存后再次扫描同一条码可复用本地数据。

## 步骤 85：建立扫码自动化测试

覆盖条码校验、去抖、缓存、远程映射、分类建议、权限、命中保存和手动回退。

**验证测试：**

- 单元测试不访问真实远程服务；
- 独立集成测试只使用受控测试条码；
- Android 模拟器或真机完成相机流程；
- iOS 相机流程由外部真机环境验收，缺失时明确记录。

# 阶段十八：本地通知

## 步骤 86：建立通知设置与权限流程

实现通知设置存储和平台权限服务。首次成功添加食品后申请权限；拒绝后不重复强制申请，在“我的”中提供说明和系统设置入口。

**验证测试：**

- 首次保存后只申请一次；
- 允许、拒绝和永久拒绝状态均正确；
- 设置持久化且清除数据后恢复默认。

## 步骤 87：实现提醒规则引擎

实现临期、今日到期、已过期和 30 天未更新四类纯 Dart 计算。默认临期规则、单品覆盖、全局覆盖、月末和时区边界以 `architecture.md` 为准。

**验证测试：**

- 覆盖不足 7 天、7—30 天和超过 30 天；
- 覆盖今日到期、已过期、单品覆盖和全局覆盖；
- 覆盖无食品、已吃完、已丢弃和已软删除食品；
- 使用固定 Clock/日期确保测试可重复。

## 步骤 88：实现每日汇总调度

默认每天本地时间 09:00 最多一条通知，将临期、今日到期和已过期合并。滚动预排未来 30 天，不申请 Android 精确闹钟权限。

**验证测试：**

- 同一天多件食品只产生一条汇总；
- 通知时间可修改并重新调度；
- 关闭每日汇总或全部提醒后取消对应通知；
- 待处理通知数量不超过平台安全上限。

## 步骤 89：实现长期未更新提醒

以有效食品的最大 `updated_at` 计算 30 天未更新；空库存不发送。用户可以单独关闭或调整天数。

**验证测试：**

- 29、30、31 天边界正确；
- 任一食品更新后重新计算；
- 空库存、全部删除或全部非有效状态时不发送；
- 关闭设置后取消提醒。

## 步骤 90：实现通知跳转与生命周期重调度

点击任一通知进入“到期提醒”。应用启动、时区变化、食品增删改、设置变化和清除数据后重新计算通知。

**验证测试：**

- 前台、后台和冷启动点击通知均进入正确页面；
- 更改时区后时间保持当地 09:00；
- 修改或删除食品后旧通知被取消；
- 清除数据后无待处理通知。

## 步骤 91：建立通知自动化与平台测试

为规则引擎、设置、权限状态和调度编排建立自动化测试；平台插件使用适配层替换。

**验证测试：**

- 单元测试不依赖真实系统时间；
- Android 验证实际权限、通知展示和点击跳转；
- macOS CI 验证 iOS 编译；
- iOS 真机通知验收缺失时记录为外部阻塞项。

# 3. V0.1.0 完成定义

只有同时满足以下条件，V0.1.0 才算完成：

- Android 可稳定启动，iOS macOS CI 无签名构建通过；
- iOS 真机、签名和 TestFlight 未验证时已明确记录为外部阻塞项；
- 食品数据全部保存在本地 SQLite；
- 用户可以通过手动或条形码扫码新增食品；
- Open Food Facts 命中、未命中和离线回退均可用；
- 用户必须通过直接到期日期或生产日期加保质期提供到期信息；
- 应用重启后数据仍然存在；
- 用户可以在列表和详情中查看该食品；
- 四类本地通知可配置、聚合、跳转和取消；
- 用户可以安全清除本地数据；
- 页面具备加载、空、错误和成功反馈；
- 路由、主题、状态管理和 Repository 结构清晰；
- 所有核心测试通过；
- 静态检查无错误；
- 除 Open Food Facts 只读查询外没有云服务、AI、远程推送或范围外功能；
- 后续开发可以在现有结构上继续扩展，而不需要重写基础层。
